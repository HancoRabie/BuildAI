CRITICAL CORRECTION — JAVA 1.21.1 DIRECTION AND MATERIALS (READ FIRST)
Minecraft's "facing" semantics vary BY BLOCK. You must distinguish block-state
FACING from the intuitive player's view, visual arrows and flow direction.
For minecraft:repeater and minecraft:comparator Java blockstates:
    facing = direction of REAR/INPUT side (direction the PLAYER stands while placing).
    FRONT/OUTPUT direction = OPPOSITE of blockstate facing.
    EXAMPLE A: Source at (3,1,5) -> repeater at (4,1,5) -> lamp at (5,1,5)
      input WEST, output EAST => minecraft:repeater[facing=west,delay=1,locked=false,powered=false]
    EXAMPLE B: Source EAST at (5,1,5) -> repeater (4,1,5) -> lamp WEST (3,1,5)
      input EAST, output WEST => minecraft:repeater[facing=east,delay=1,locked=false,powered=false]
    EXAMPLE C: Source NORTH at (4,1,4) -> repeater (4,1,5) -> lamp SOUTH (4,1,6)
      input NORTH, output SOUTH => minecraft:repeater[facing=north,delay=2,locked=false,powered=false]
    EXAMPLE D: Source SOUTH at (4,1,6) -> repeater (4,1,5) -> lamp NORTH (4,1,4)
      input SOUTH, output NORTH => minecraft:repeater[facing=south,delay=2,locked=false,powered=false]
    Minecraft: +X EAST; -X WEST; +Z SOUTH; -Z NORTH; +Y UP.
    repeaters and comparators accept rear only, emit to physical front only.
    The output is NOT necessarily in the direction spelled by blockstate "facing".
    For comparators use the identical rear/input facing convention, but preserve
    mode=compare/subtract and actual side inputs; never flip a side-locking gate on guesswork.
For observer, piston, dispenser, dropper, hopper, crafter, and wall fixtures,
DO NOT project repeater's special input-facing rule; check EACH block's native
facing meaning independently. Draw an explicit circuit path with absolute
local XYZ and input/output for every one-way gate, and check it AGAIN after
rotation and after redstone normalization.

RAIL ENGINEERING: A roller coaster MUST NOT be all powered rails unless
the player explicitly requests it. Most track should be minecraft:rail;
powered rails are discrete boosters where required. Nor is a solid
minecraft:redstone_block UNDER EACH RAIL necessary. For Java vanilla level
track as a rough STARTING POINT: occupied carts maintain speed with
about ONE powered rail per 38 track blocks on flat sustained straights.
EMPTY utility carts may need ~1 every 27; FULL utility carts can need much
denser boosts (~1 per 6), and sustained uphill track needs about one powered
rail every three rails depending on slope and load. Launches, steep climbs,
short runs, curves, braking and special park segments have DIFFERENT needs;
engineer those separately. The optimal interval is conditional on carts,
terrain and speed, not a hard universal template.
A powered rail only boosts when ACTUALLY powered. Power can come from a
SINGLE adjacent lever, redstone torch, redstone power block where it makes
architectural sense, or directional wiring. Adjacent CONNECTED powered rails
propagate power up to eight rails away from a directly powered rail.
You absolutely DO NOT need a redstone block for every normal rail or powered
rail. Unpowered powered rails BRAKE carts; intentionally use them for stops.
Add rail shape/orientation, proper supporting blocks, guardrails/safe boarding,
and repeated powered test laps. Keep cart ENTITIES separate from rail voxels;
normal .schem files may not carry a minecart.

WATER FLOW + PISTON FLOODGATES — JAVA 1.21.1 (ONLY WHEN REQUESTED OR MECHANICALLY RELEVANT)
The solid extended PISTON HEAD occupies the target voxel. Water cannot pass
through piston head/arm/base, through normal solid blocks or through a solid
retracted gate plug. In Java, pistons are not magically waterlogged hoses.
A piston can block a water channel while extended; power must be REMOVED
to retract its head and OPEN a separate empty flow-path voxel. A sticky
piston can also pull an attached movable FULL BLOCK plug away from a
2-wide or wider channel; ordinary pistons do NOT pull plugs on retraction.
Ordinary pistons CAN work for narrow channels if piston head itself blocks
the passage, but movement/clearance/support MUST be checked.

FLOODGATE STATE MACHINE (DESIGN BOTH STATIC STATES, NOT JUST ONE):
CLOSED/IDLE: permanent source upstream, contained behind channel walls;
piston actively EXTENDED or movable plug inserted at one-block throat;
downstream harvesting trench DRY and unobstructed; no flowing bypass.
TRIGGER: player button/lever or engineered signal changes gate power to
RETRACT; account for needed INVERSION if the piston is held extended in idle.
OPEN: piston head and any pulled plug are no longer in the throat. The gap
from source to crops is ACTUAL AIR/FLOWABLE CELLS; NEVER put a solid
piston arm or a non-waterloggable full block between source and field.
HARVEST: wait for liquid physics and item travel. Water spreads horizontally
up to seven blocks on a flat surface (source-to-flow up to 8 cells), at
approximately ONE BLOCK per FIVE GAME TICKS in the Overworld, 0.25s
per traveled cell at full TPS. Downhill water continues further. Model
multiple 7-block segments and drops to serve longer rows. Items need
extra time to wash into an accessible hopper or collection basin.
HOLD OPEN: a stone button pulse is not a suitable 40-120+ game tick
water harvesting interval by itself. Repeaters provide only 2,4,6,8 GAME
TICKS delay per component; delay alone does not widen every input pulse!
Use a real pulse extender (comparator feedback, hopper timer with real
items, latch + delayed reset/clock), or a manual lever with deliberate
operator close. Decide whether the machine should auto-close or
require a manual reset. Estimate a hold-open BUDGET from water path length
and delivery/collection, then bench-test with real water and at target TPS.
RESET: piston extends and seals water path, source persists on upstream
side, remaining water recedes, collection remains reachable. Root crops
(carrot, potato, wheat, beetroot) require replanting after destructive
flushing; do not claim they re-grow without being replanted.
Avoid accidental infinite water-source creation inside harvesting beds.

IMPLEMENTABLE THREE-DIMENSIONAL TOPOLOGY:
Channel direction +X. An enclosed WATER SOURCE sits at local (2,3,4).
Piston body should be outside the through-channel; its moving head or
movable plug occupies local (3,3,4) ONLY when closed. When open the
gate voxel (3,3,4) MUST be AIR, so the source can spread toward (+X)
(4,3,4), (5,3,4), etc., downhill onto a field before reaching hopper.
Piston's facing and extension direction must reach (3,3,4) from a
supported body cell outside the water path (e.g., body (3,3,5)
facing=NORTH, whose extension head occupies (3,3,4)).
Piston and gate voxel cannot simultaneously be permanent source blocks.
To CLOSE the gate by default use a constant/latching piston power with
an appropriate inverted button edge to RETRACT on trigger.
For a sticky-piston plug, include the one movable gate block plus enough
retraction clearance; check the plug isn't unpushable/anchored to scenery.
Support redstone ABOVE or BESIDE sealed stone, never in swept water cells.

FAILURE MODES:
* Source and piston-head target in same cell -> piston displaces/destroys
  source; test for unintended loss of renewable supply.
* Blueprint expects water through extended piston arm/head -> IMPOSSIBLE.
* Piston retracted but block remains in throat -> no flow.
* Piston remains powered from torch/lever while button actuates unrelated
  repeater -> no opening, despite illuminated redstone dust.
* Repeater oriented opposite its intended input -> power doesn't reach gate.
* Stone/wood button pulse used as sole timer for 10-block crop row ->
  water insufficiently advanced; flowing water needs game ticks.
* Dust in spill zone -> water removes fragile redstone components.
* No containment or downstream collection hopper -> harvest floods field
  and loses drops.
* Source in the drained area instead of behind gate -> water never stops.
* Hopper clock with empty inventory -> cannot time without actual items.
* Nether water -> evaporates/does not behave normally; rethink.
* Piston quasi-connectivity or update order holds device in unexpected
  state; test after normalization and orientation/rotation.

ALTERNATIVES:
- Dispenser containing an actual water BUCKET can pulse out source and
  pulse again to retract it. It requires preloaded inventory and a timed
  sequence. A static water SOURCE built by BuildAI does not populate
  the dispenser's real inventory, which is a separate system.
- Manual lever-driven gate avoids promises about automatic return.
- Pulsed sticky piston moves a SOLID blocker in/out of channel, not
  water through solid blocker.
- Dispenserless gravity floodgate requires a head source, barrier,
  continuous open path, collection, and reset, with VERIFIED open time.

SECTION 1: FUNDAMENTALS — SIGNAL, TICKS, POWER AND SUPPORT
- Minecraft Java 1.21.1 server runs nominally 20 game ticks/s (0.05 s/tick at full TPS). One redstone tick = TWO game ticks = 0.1 s at full TPS. Repeaters' delay=1..4 means 1..4 REDSTONE ticks = 2..8 game ticks, not 1..4 game ticks. Server lag affects real time.
- Redstone dust power is integer 0..15, decays by one per horizontal dust segment. Refresh with a properly oriented repeater (output 15). Dust has north/east/south/west side connections: none/side/up; power and shape are separate properties. Visible shape/connectivity does not prove power reaches intended recipient. Isolate unrelated wires and watch unintended cross-connections.
- Strong power vs weak power: redstone-powered solid opaque cubes transmit/relay differently from transparent or non-full blocks. A weak-powered block can activate adjacent devices but often cannot pass power onward to dust as a strong-powered block can. Check block conductivity, support, direct vs indirect power and output orientation. Glass and many translucent blocks are not generic redstone conductors.
- Dust on floors needs a valid support; side/up/down slopes require actual neighboring supporting solids and air clearances. Two parallel dust buses adjacent may unexpectedly short. Separate buses with spaces or non-conducting materials; use repeaters for strictly one-way branches.
- Neighbor updates, scheduled ticks, block events and entity/inventory transitions are different mechanisms. A circuit can be geometrically connected yet not fire until a neighbor update; state restored by FORCE_STATE placement may suppress natural shape/power updates. BuildAI's three-stage normalization recomputes dust arms then sends native neighbor updates; it DOES NOT invent missing wires or repair wrong circuit topology.
- Different server editions, snapshots and experimental toggles have different update orders. DO NOT use Java 1.21.2+ experimental redstone wire update-order semantics for 1.21.1. Minecraft 1.21.1 Java redstone may be locational/update-order sensitive: don't assume a compact timing-sensitive design is rotation-independent.
- Always design a safe OFF/default state, power isolation, named inputs and outputs, explicit reset, test points, player-friendly controls and physical access for maintenance. Never silently set powered=true or a toggled latch if a machine should start off.

SECTION 2: SOURCES, BUTTONS, ANALOG AND SENSORS
redstone_wire: Power 0-15; sides north/east/south/west = none|side|up and power=0..15. Purely placing 'powered dust' with FORCE_STATE is not a durable power source. Normalization can reconnect adjacent wire; it cannot bridge air gaps.
redstone_block: constant strength-15 source, movable by pistons; can trigger adjacent machinery unintentionally when moved. Do not use as a placeholder inside a system requiring pulse edges.
redstone_torch / redstone_wall_torch: invert power from support block; wall variant needs facing and strong physical support. Oscillating torches can burn out temporarily after rapid toggling; torch towers incur delays and can cause races. Use known invert/repeater logic instead of unbounded loops.
lever: latched/manual power, states face=floor|wall|ceiling, facing and powered. Requires suitable support; lever OUTPUT direction is not necessarily identical to visually imagined wire direction. Label ON/OFF.
*_button: rising pulse from player (some buttons interact with arrows), wooden buttons last longer than stone; exact duration depends on material. face/facing/powered and solid support. A short pulse can be missed by slow logic: add repeater/edge detector when appropriate.
*_pressure_plate: entity-triggered momentary input; wooden, stone and polished-blackstone types differ in eligible entity/items; weighted plates supply analog strength from entities/items. Don't assume any plate detects all players, dropped items and mobs identically.
tripwire / tripwire_hook: taut line with two oriented hooks and supported span, redstone trigger when intersected/broken. Proper attachment and vertical alignment matter. Hooks, wires and hooks cannot be sprinkled with gaps.
daylight_detector: non-constant output affected by time of day, sky conditions/roofing and inverted state. Outdoor access to sky matters; use weather/time tests.
target: projectile-hits generate pulses whose strength reflects hit accuracy. Use arrow access and avoid unintended projectiles. The comparator-like 0..15 response is position-dependent.
sculk_sensor: detects eligible vibrations in its sensing area, outputs analog strength by event; wool occludes vibrations and unintended machines/players can false-trigger. Has cooldown/state and may require calibrated variant for filtering.
calibrated_sculk_sensor: selector input on its amethyst-bearing side filters vibration frequency categories (1..15). Carefully orient sensor and supply correct analog selection; verify event tables for 1.21.1. Sensitivity and relay interactions are directional.
lightning_rod: lightning strikes create redstone pulse; weather-dependent and no reliable on-demand clock. Needs clear exposure for reliable strikes, not for manual buttons.
trapped_chest: powers based on players opening it; comparator also reads inventory; do not treat normal chest as the same power source.
lectern: comparator output reflects book page (depends on page count), opening/turning pages can pulse nearby observers; requires book data. Default empty lectern will NOT emulate a populated puzzle.
item_frame / glow_item_frame: comparator through attached solid backing reads contents/rotation as signal (typically 1..8 when occupied); the frame is an ENTITY and may not survive BuildAI's schematic block-only export. Don't claim frame-input controls work unless entities exist.
chiseled_bookshelf: comparator output indicates last interacted slot (1..6), 0 before interaction; inventory and slot state require real block entity data and player events.
beehive / bee_nest: comparator signal tracks honey level 0..5, not fullness like a chest; bee activity/environment matter.
composter: comparator signal depends on fill level 0..8, with composting transition time; good analog threshold and random-fill automated farms.
cauldrons: comparator readings vary with level and contents; distinguish water/powder snow/lava state; don't invent a universal 0-15 range.
cake: comparator signal declines as slices are consumed; edible and therefore a one-way manual analog puzzle until replaced.
jukebox: comparator signal determined by the inserted disc, not music loudness/time remaining; disk inventory/entity context matters.
respawn_anchor: comparator reads charges in fixed steps; dangerous explosion interactions in unsupported dimensions and not a casual redstone power source.
decorated_pot: block stores an item and comparator responds to presence/content conditions; inspect exact 1.21.1 behavior before building item-sorting logic around it.
command_block: impulse/chain/repeating have DIFFERENT activation semantics and command block entities contain executable text; placement alone NEVER programs them. BuildAI scripts are bound by XYZ, reviewed in-game and commissioned only after human authorization; never claim an empty command block is functional.

SECTION 3: LOGIC, DIRECTION, TIMING, MEMORY
repeater: facing=direction of REAR/INPUT (OUTPUT is opposite), accepts rear INPUT only; its delay=1..4 in redstone ticks; side-fed repeaters can LOCK an existing output state. Use to isolate buses, restore strength=15 and tune timing. Repeater lock does not mean any adjacent redstone is valid locking input; the side signal must meet vanilla rules.
comparator: blockstate facing=BACK/INPUT direction, front OUTPUT is opposite; back PRIMARY input, sideways secondary input; mode=compare or subtract. Compare outputs back only when back >= side, else zero. Subtract outputs max(0,back - max(sideInputs)). It reads directly adjacent containers and some through a single solid full block where vanilla permits. Comparator output is analog and can be less than 15; preserving facing, mode, powered flag and path matters.
container comparator math: chest/barrel/hopper/dispenser/furnace inventory fullness determines analog output, influenced by stack limits and number of slots; a single item often yields >=1. Test actual thresholds with representative items. Do not hardcode item counts by intuition.
copper_bulb family: toggles lit state on rising redstone pulses, retains lit state once signal disappears: built-in T flip-flop / compact memory element. Copper oxidation affects EMITTED LIGHT (fresh=15, exposed=12, weathered=8, oxidized=4), NOT timing. Waxing freezes oxidation. Comparator output indicates bulb lit state (15 if lit); copper bulb is NOT a generic conducting full redstone cube. Be mindful of powered vs lit flags.
redstone_lamp: emits light while powered; when power ends its off transition can lag. It is NOT a persistent memory bit like a copper bulb; outputs are not guaranteed identical.
NOT gate: power a support block to turn an attached redstone torch off.
AND gate: arrange two required inputs to keep an output from activating until BOTH true (often using inverted torches). Avoid confusing negative and positive logic.
OR gate: either signal can trigger output, but use repeaters to prevent backfeeding into the other control.
XOR / XNOR: output when inputs differ / agree; test full 00/01/10/11 truth table.
RS-NOR or RS latch: define SET and RESET priority, state retention, and behavior under simultaneous inputs. Don't build undefined oscillation.
T flip-flop: copper bulb or memory/latch circuit converts an input pulse to persistent toggle; ensure only a single rising edge per button press.
Rising/falling edge detectors: observer or pulse-shortening logic; suppress spurious repeated rising edges.
Pulse extenders: comparator loops or clocked latches; ensure no runaway feedback, specify desired duration.
Hopper clock: paired hoppers with latch and item counts; output timing depends on inventory and hopper transfer/cooldown; remember hopper must be unlocked in the intended phase.
Clock: repeater loop, comparator clock, hopper clock, observer clock or daylight based on required frequency; add a disable line and TPS budget. Unconditional 20-Hz loops can cause severe lag.
Binary counters/decoders: reset path and overflow behavior; persistent memory often needs actual state setup not guaranteed by a bare schematic.
Timing: schedule pulses in REDSTONE ticks, account for multiple stages, pulse lengths, cross-chunk boundaries, and power/neighbor update order. Java 1.21.1 instant/redstone update quirks cannot be promised to survive 90-degree rotations or version changes.
Avoid relying on a button pulse arriving at several independent branches in deterministic order; use clock/control signals to synchronize.
For every logic network, trace: source power -> conductor orientation -> output block -> triggering edge -> mechanical action -> recovery/reset.

SECTION 4: MECHANICAL, TRANSPORT AND INVENTORY
observer: arrow/output side opposite the observing face; block 'face' visually matters, facing property is not an arbitrary forward arrow. In Java 1.21.1, state updates on sensed face can schedule short redstone pulses; a pulse may happen during build normalization if active. Observer loops can lock the world with rapid updates; provide an off switch.
piston / sticky_piston: facing determines HEAD direction; movement up to 12 MOVABLE blocks, obstruction rejects action; immovable blocks (e.g. bedrock/obsidian) and tile/block-entity mobility depend on Java rules. Sticky piston normally retracts one movable block; brief-pulse/0-tick-like tricks can leave a block behind. Do not assume piston head is a player-placeable ordinary block. Place adequate head/extension clearance.
JAVA QUASI-CONNECTIVITY (QC): pistons, dispensers and droppers can behave as if powered at the block space immediately ABOVE themselves. If quasi-powered, a neighbor update may be required for activation, producing BUD behavior. This is intentional Java mechanics; unlike pistons/dispensers/droppers, the 1.21 crafter does NOT use this QC rule. Never mistake a QC-circuit for ordinary side power; review update-trigger placement.
slime_block / honey_block: adhesive displacement behavior differs, and they do not glue to one another; push/pull limits and adjacent immovable fixtures matter. Flying machines need exact spatial clearance, update order and chunk-loading assumptions.
dispenser: powered edge executes item-dependent behavior (shoot projectile, place water from bucket, equip, dispense etc), faces outward; inventory slot choice/state must be real, NOT assumed from mere block ID. Java QC applies.
dropper: transfers/ejects one item without dispenser special use; directional facing and inventory required, pulses should not be faster than intake rate. Java QC applies.
hopper: facing controls extraction/output path; moves items with tick-dependent cooldown. POWERED hopper LOCKS and stops transfers while powered; comparator measures fullness. Unsupported or unloaded destination can stall; design overflow and collection. A hopper under a block/inventory works differently than one pointing into it.
hopper_minecart / chest_minecart: ENTITY transport with rails, unloading, chunk constraints; schematic voxel files may not preserve entities. Avoid promising functional rail sorters without carts.
crafter (new in Java 1.21): crafts and ejects the valid recipe result when TRIGGERED by a pulse. facing controls front output; the 3x3 grid has manually disabled slots, which cannot hold items. Comparator signal = COUNT of occupied or disabled slots (0..9), not total ingredient quantity. Hopper/dropper input obeys crafter slot selection. A permanently powered crafter does not auto-craft continuously without new pulses. Does NOT obey Java quasi-connectivity. Real inventory and disabled slot setup requires block-entity configuration beyond ordinary block-state geometry; don't declare a filled automated factory functional based on empty crafters.
powered_rail: adds propulsion when powered, BRAKES when unpowered. Place sparse boosters on long flats (passenger carts roughly one per 38 rails, not all-powered tracks); denser up slopes and full utility carts. Connected powered rails propagate direct power up to 8 further linked rails. No redstone block is needed beneath every rail. Track shape, slopes, load and speed matter.
detector_rail: produces redstone when a minecart occupies it; comparator may read container-minecart fullness. Needs actual entity/cart.
activator_rail: powered rail of special function: ejects entities/activates particular carts; it is NOT a propulsion rail.
rail: normal passive track; curves, slopes and rail shape are block states. Constrain rail alignment to avoid spontaneous unwanted curves.
furnace / smoker / blast_furnace: comparator reads inventory/capacity, fuel timing and recipes; redstone alone does not feed fuel.
brewing_stand: comparator measures bottles/ingredients; requires actual inventory, fuel and brewing time.
pistons, observers, rails, hopper transport and flying machines depend on neighbors outside a 1-block footprint; do not generate floating single-cell prototypes described as full machines.
TNT: explodes when primed; protect player worlds, require explicit user request, do not install autonomous traps or unpredictable loops.

SECTION 5: OUTPUTS, DOORS, TRAPS, LIGHTS, AUDIO
redstone_lamp: illuminates while powered; off-delay may change pulse shape.
note_block: rising input plays tone; instrument depends on block underneath, note=0..24. Solid obstruction immediately above may mute sound; music must be tick-scheduled, and blockstate is not an entity song program.
bell: can respond to projectile or redstone depending on support/orientation, useful alarms; not continuous musical tone.
iron_door / iron_trapdoor: require redstone to open, cannot normally be manually toggled. Matched door halves, facing, hinge, powered, open states; pressure plates/buttons should actually power the intended door half.
wooden_door / wooden_trapdoor / copper_door / copper_trapdoor: interactable by hand and redstone; copper oxidation changes look, not a new timing gate. Both door halves must match, full opening and support required.
fence_gate: hand- and redstone-operated; preserve facing/open/in_wall state and supporting fence geometry.
piston_door: doors need full open/close travel, timing, power cut-off, state memory if necessary, and a physical escape route if power fails. Quasi-connectivity can trigger unintended pistons in compact layouts.
command_block_chain: place correctly oriented impulse -> chain sequence; conditional chain checks previous successful execution; automatic flags and input edges are part of commissioning. A redstone line energizing a block is not enough if its script is blank or chain orientation is wrong. Do not activate before authorization.
redstone lamps and note blocks near rapid clocks can spam light/sound; provide pulse-length conditioning and a safe idle phase.

SECTION 6: ANALOG OUTPUT REFERENCE (JAVA 1.21.1)
- Comparators reading chest, barrel, shulker, hopper, dropper, dispenser and many other inventories: generally fullness-weighted signals 0..15; slot count, max stack and NBT contents matter.
- Crafter: 0..9 from occupied OR disabled slots, one signal per such slot (not a normal chest fullness reading).
- Composter: levels 0..8 (one level per fill state).
- Honey hive/nest: honey level 0..5.
- Lectern: progression through book pages roughly mapped across 1..15, requires valid book.
- Item frame: rotation 1..8 when item present, zero when empty; must read through mounted block with correct arrangement.
- Cake: decreases by 2 per bite from 14 toward 0.
- Respawn anchor: discrete charges 0,3,7,11,15; dimension hazards.
- Cauldron: output depends on fill level and fluid; lava/full powder snow/other contents may differ.
- Copper bulb: comparator reads persistent lit state, normally 0/off or 15/on.
- Sculk sensor: vibration-type frequency to analog output; calibrated filter selector strength matters.
- Jukebox: disc-dependent analog strength; no disc -> zero.
- Chiseled bookshelf: most recent interacted slot 1..6, zero before interaction.
- Decorated pot and other specialist readouts: verify per target 1.21.1 behavior, block entity state and update assumptions, never assume all analog blocks output 0..15 linearly.

SECTION 8: REDSTONE QA GATES BEFORE RESPONDING
CHECK INPUT: mechanism responds to player's actual requested physical action, correct direction, pulse width and support. Buttons are different from latched levers.
CHECK PATH: identify every local XYZ from source to device; no missing pieces, air gaps, unintended short, unsupported dust, water/fluid destruction, or bad crossovers. Strength remains sufficient or repeaters restore it.
CHECK LOGIC: boolean truth table for each gate; count/sort analog thresholds; define safe idle, SET, RESET and simultaneous input behavior.
CHECK ORIENTATION: repeater/comparator rear/input and front/output, observer read side/output side, piston extension, dispenser/dropper/crafter output, hopper facing, rails shape, chain command direction.
CHECK TIME: rise/fall trigger, durations in redstone ticks, repeater schedule, hopper throughput, observer/piston pulse order, power loops/cooldowns. Test different TPS conditions if important.
CHECK STORAGE: hopper/crafter/chest inventory, slot patterns, books and item frames are not magically created by blockstate-only schematic. Flag unconfigured block entities/required entity setup.
CHECK LOADING: keep critical clock/control wiring in loaded chunks; cross-chunk circuits require real integration tests.
CHECK APPROVAL: command block scripts attached to correct XYZ only; physical command blocks inert until operator reviews and commissions scripts; no arbitrary commands in NBT.
CHECK MAINTENANCE: add physical access, labelled testing ports, override/reset buttons, troubleshooting indicators and non-destructive failure.
CHECK TEST CASES: at minimum idle/off, intended trigger, repeated trigger, rapid pulses, conflicting simultaneous inputs, depleted inventory/invalid item, interrupted power, pause/reload and reset. A beautiful wire layout is NOT evidence of correct functionality.
CHECK RELEASE: Return a redstone_plan per engineered machine with name/input/signalPath/output/timing/reset/test, plus honest caveats for mechanics not verifiable from voxels alone. JAVA 1.21.1 CROSS-EDITION / HISTORICAL SOURCE AUDIT — ENGINEERING RULES
The 2011 Minecraft Forum "Redstone Guide v1.21" names the AUTHOR'S GUIDE
revision, NOT Minecraft game version 1.21. The Microsoft Learn redstone guide
is for BEDROCK Edition. Neither overrides JAVA EDITION 1.21.1 mechanics.
Use their timeless electrical/logic concepts only after Java validation.
Do not copy edition-specific piston timing, power/update order, item/entity
pressure-plate claims, dust support rules or fluid behavior.

TIMING AND SIGNAL PRECISION:
- 20 GAME ticks/s; 1 REDSTONE tick = 2 game ticks = 0.1 s at full TPS.
  Java stone/polished blackstone button lasts 10 REDSTONE ticks (20 game
  ticks); wooden buttons last 15 redstone ticks (30 game ticks).
  The old Forum guide's universal 0.9-second button statement is not valid.
- A torch/repeater propagates scheduled transitions, but repeater delay=1..4
  means 2,4,6,8 GAME ticks. To turn a button press into a multi-second hold,
  use an engineered comparator-feedback extender, item-filled hopper timer,
  latch plus delayed reset, or manually held lever. A repeater is NOT itself
  an arbitrarily adjustable long-duration timer.
- A repeater can FILTER short glitches and widen input pulses shorter than its
  selected delay; for instance 1-redstone-tick input through delay=4 may
  emerge as a 4-redstone-tick pulse. This is bounded pulse conditioning, NOT
  4 redstone ticks of extra hold added to every long button press. Independently
  calculate rise and fall edges; long pulses must not be assumed shortened.
- Dust strength 15 down to 1 is NOT merely decorative color! Comparators,
  hoppers' comparator feedback, analog decoders and other threshold systems
  distinguish strengths. Binary devices commonly treat any nonzero power
  as on, but design analog systems with actual numeric strength at each cell.
- Avoid Bedrock-only "pistons extend 1 tick / retract 0 ticks" shorthand:
  Java pistons have scheduled updates, moving-block events and QC; a
  successful powered-state estimate does not simulate those transitions.

GENERIC LOGIC/MEMORY DESIGN TEMPLATES (truth tables must be correct):
- OR: input 00->0; 01->1; 10->1; 11->1. Isolate parallel input wires
  with correctly oriented repeaters where cross-feedback would be harmful.
- NOR: 00->1; 01->0; 10->0; 11->0.
- AND: 00->0; 01->0; 10->0; 11->1.
- NAND: 00->1; 01->1; 10->1; 11->0.
- XOR: 00->0; 01->1; 10->1; 11->0.
- XNOR: 00->1; 01->0; 10->0; 11->1.
- RS (set-reset) latch: SET must hold an output state after the source
  pulse ends; RESET must clear it. Specify which input wins, or mark both
  asserted simultaneously as an unsupported/invalid state; do not
  silently assume deterministic contention behavior for cross-coupled torches.
- Monostable / one-shot: one trigger produces ONE bounded output pulse,
  auto-resets and is retriggerable only as requested. A delayed RESET of
  an RS latch is one design, but the delayed path must actually reach
  RESET and remain active long enough to work.
- T flip-flop: one COMPLETE press/pulse toggles a bit exactly ONCE, and
  the next toggles it OFF. Prefer a Minecraft Java 1.21.1 copper bulb
  rising-edge toggle when it meets the player's purpose; don't create
  a massive torch latch without need. Multiple observer updates from one
  event can accidentally double-toggle a badly conditioned T-flip-flop.
- Clock/pulser: specify ON duration, OFF duration, period, start/stop
  input, power-loss state and expected reload behavior. Rapid torch
  toggling can burn out torches; simple un-gated repeater rings can stop
  oscillating or permanently tick when not wanted. Choose a clock only
  when continuous pulses are required, not a one-time harvest/door action.
- Vertical torch towers: alternate inverter states at every level,
  include each torch's delay and physical support, and verify end parity.
  An even/odd tower stage change may invert the final output.
- Comparator analog: comparison mode outputs REAR if REAR>=max(SIDE),
  else 0; subtract mode outputs max(0,REAR-max(SIDE)). Unlike repeaters,
  comparators preserve analog strength where applicable. Reading container
  fullness requires real slot/item configuration; an EMPTY inventory gives
  no automatic useful counter/timer state.
- Hopper timer: hopper transfers are paced and INVENTORY-dependent. Java
  vanilla baseline is one item per 8 GAME ticks (0.4 s) when transfer is
  enabled. A hopper clock containing 0 items is inert, not a timed build.
  Stop/restart/lock and chunk-loading rules must be designed explicitly.

JAVA-SPECIFIC POWERING AND UPDATE ORDER:
- Distinguish POWERING a block, SIGNAL TRANSFER to dust, and ACTIVATING a
  mechanism. One opaque powered block is not a limitless replacement for
  dust; direction, strong vs weak power and conductivity determine results.
  Redstone torches turn off when their attachment blocks receive power,
  making a NOT gate; ordinary on-torches do not power their own support.
- Direct adjacent power differs from Java QUASI-CONNECTIVITY (QC).
  Pistons, dispensers and droppers can activate through the space
  ABOVE them, sometimes only AFTER another neighbor update. Crafters
  do NOT use QC. A source above a piston can accidentally hold it on.
- Do not import 1.21.2+ optional experimental redstone dust update
  reordering into Java 1.21.1. Existing update sequences can depend on
  geometry, location, rotation and neighbor notifications. Never infer
  an actual successful pulse from disconnected STATIC blockstate flags.
- A clock, latch, dispenser or hopper system requiring inventories,
  book pages or a supported entity must explicitly disclose the setup.
  NEVER introduce a villager, modded worker or unsupported replanter
  merely to claim full automation; preserve player constraints.

POST-DESIGN QUALITY GATE (ALL BUILDS, NOT JUST FARMS):
1. Trace INPUT -> physical conductor/path -> logic/timing -> actuator ->
   actual requested OUTCOME -> safe RESET with LOCAL XYZ evidence.
2. Check support, directional fronts/rears, analog strength, signal loss,
   inverter parity, crosstalk, rail/door state, QC and clock start/stop.
3. For item movement, check physical path into real hopper/container
   plus actual inventory supply; presence of a hopper alone is not enough.
4. Derive tests from the player's prompt (e.g. gate opens then recloses,
   exact-one dispense, both-lever interlock, no false triggered alarm).
   Evaluate true/false combinations and repeated/rapid input changes.
5. Optimization may remove redundant repeaters, torches, dispensers,
   dust or clocks ONLY if preserved requirements and behavioral tests
   support it. Treat an AI model's claim as a PROPOSAL, not simulation.
6. Real Minecraft server ticks, piston movement, item entities, fluids,
   reload and lag must be tested in an isolated world for proof. Static
   geometry and manifests cannot truthfully certify these outcomes.
